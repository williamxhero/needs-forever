## Problem Statement

正常路径上的持续推进不足以证明可恢复。judge 失败、服务错误、线程卸载、子进程退出、漏通知或发送后断线，都可能让程序停止、丢失动作或重复执行。需要完成恢复行为与全量验收，证明 v0.1 的真实支持边界。

本子 SPEC 为总 SPEC #19 的 S3，对应“阶段三：恢复验证”。依赖 S2 的真实判断和独立验收能力，最终统一核验 S1、S2、S3 的成果。

## Solution

补齐固定退避、错误分类、重复失败换路、同线程恢复、未确认发送核对及唯一周期 reconcile。运行完整 15 场景矩阵和要求的真实用例，交付可复现示例与准确报告，再按总规格统一完成条件交付。

## User Stories

1. 作为任务负责人，我希望临时服务或网络失败后持续重试，以便恢复后继续同一个目标。
2. 作为任务负责人，我希望超时和非法判断能重试，以便偶发 judge 失败不结束任务。
3. 作为任务负责人，我希望重复失败触发调查或换路，以便次数阈值不会直接导致放弃。
4. 作为任务负责人，我希望看到错误类别和下次重试时间，以便区分恢复等待与停止。
5. 作为任务负责人，我希望真实账户或额度问题有明确等待条件，以便不会把所有 429 误判为欠费。
6. 作为任务负责人，我希望线程卸载或受管服务退出后恢复同一 worker，以便保留上下文与产物。
7. 作为任务负责人，我希望发送结果不明时先核对历史，以便不盲目重发。
8. 作为任务负责人，我希望漏掉结束通知也能补处理一次，以便持续推进不依赖每条通知完整送达。
9. 作为任务负责人，我希望检查点恢复保留计数、时间和目标，以便不绕过用户限制。
10. 作为任务负责人，我希望暂停和完成在恢复后仍稳定，以便计时器和旧结果不能唤醒任务。
11. 作为任务负责人，我希望长工具调用不会仅因静默被杀掉，以便有效工作得以继续。
12. 作为任务负责人，我希望报告区分真实、模拟和未运行，以便准确了解产品能力。
13. 作为任务负责人，我希望三个子规格和总验收都成立后再关闭总 SPEC，以便阶段成功不冒充整体完成。

## Implementation Decisions

- worker、judge、启动连接共享错误分类。临时网络、服务不可用与明确可恢复限流自动退避；确需用户恢复的认证、账户或额度错误在既定办法无效后记录具体证据和恢复条件，进入 WAIT_EXTERNAL。未知错误诊断，不默认硬阻塞，也不把所有 429 当作欠费。
- judge 超时默认 120 秒，退避默认 5、15、60、300 秒，之后保持 300 秒；只有确认旧 judge 结束或中断才创建新线程。次数本身不触发 PAUSED 或 WAIT_EXTERNAL。
- 恢复期间保持 ACTIVE／RECOVERING，打印原因、累计次数和下次重试时间。默认不限制总回合和总活动用时；显式限制达到时 PAUSED／user_limit，跨恢复保留累计值，须显式提高或移除限制才能继续。
- 连续重复失败阈值默认 3，以错误签名、相同指令和缺少新工具结果触发下一快照的调查或换路要求；没有进展评分，不用反复说“继续”代替恢复证据。
- thread/closed 或 notLoaded 恢复原 worker 并回到待处理判断或发送；app-server 异常退出先确认旧子进程结束，再重建握手、恢复明确 ID 并核对历史。历史损坏、删除或未知其他写入者时保留任务和未完成状态，不悄悄换线程。
- 发送状态不明先核对原线程运行状态和消息／回合历史。发现对应执行就追踪，确认未执行才允许补发；delivery_id 用于关联，不是服务端幂等键。
- 明确 resume 递增版本；旧待发送动作确认未执行后按当前目标重新判断，已执行则跟踪原回合。即使来源回合已在 handled_turn_ids，仍不能跳过 pending_action 核对。
- 每 30 秒只通过同一 reconcile 入口核对活动与历史，发现遗漏终止回合时进入原事件入口补处理；保持活动工具运行，不按自然语言静默时长强制重启，不新增第二条调度循环。
- 暂停、等待、完成统一撤销未发送动作和重试，所有恢复与验收结果再次核对版本和 ACTIVE。监督程序自身退出后通过明确 resume 恢复，不实现操作系统自动拉起。
- 复用准确版本的 S1、S2 证据，追加受影响回归及本阶段故障证据，形成总规格要求的完整运行报告。模拟通过不能替代要求的真实事件与模型闭环。

## Testing Decisions

复用公开 CLI → 受管协议、进程与历史 → 状态、产物、独立验收的边界。使用模拟传输稳定复现故障窗口，真实测试仅操作隔离演示和本程序自有进程，不以进程存在或成功退出代替业务完成。

- [ ] T09 simulated：judge 超时、非法 JSON 后恢复，无误判完成或隐藏重试次数上限。
- [ ] T10 simulated：可恢复服务错误退避继续，并区分普通限流与账户额度错误。
- [ ] T11 live：线程卸载与所管理 app-server 退出后均恢复同一 worker，原产物保留并继续。
- [ ] T12 simulated：发送后断线、响应丢失时先核对历史；已执行的不重发，确认未执行的才补发。
- [ ] T14 simulated：回合或时长限制达到后保持 user_limit 暂停；未配置时不触发；累计值跨恢复保留。
- [ ] T15 simulated：遗漏终止通知通过周期核对补处理一次，重复事件不增加工作。
- [ ] T08 live：worker、judge、验收期间分别暂停，相关调用结束且迟到结果不改变 PAUSED。
- [ ] 补验 T06 的等待稳定性、T07 的过期结果门禁、T13 的不悬挂请求处理，以及 prepared／已发送未确认／已确认三个恢复窗口。
- [ ] 对 #19 全部 T01–T15 提供通过证据；真实至少覆盖 T01、T02、T03、T04、T05、T08、T11，其余可 simulated。允许报告 not_run，但有未满足的必需项不得宣称本项或总规格验收完成。
- [ ] 提交可运行 CLI、依赖锁、配置与判断说明、演示工作区、独立验收、真实与模拟入口、报告和可追查示例，准确记录系统与 Codex 版本、命令、线程 ID、事件序列和验收输出。

退出条件：完整矩阵及必需 live 范围成立，恢复保持原目标、身份与暂停／完成门禁，所有交付物可复现；完成后统一核验总 SPEC 的验收与交付条件，不能仅凭子 Issue 已关闭判整体成功。
