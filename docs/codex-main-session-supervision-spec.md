# 主 session 作为 worker：Stop hook 驱动的独立监督与原会话续跑

## Problem Statement

当前 Needs Forever 插件在用户调用 `needs-forever:supervise` 的 Desktop 主 session 之外，另建 app-server 和 worker。用户在原聊天中无法直接看到执行过程，也无法自然地在原执行上下文中介入。即使后台 worker 正在工作，原聊天中的进度仍主要依赖额外查询。

用户要求调用技能的主 session 本身就是 worker：技能启动独立 Node.js 监督进程 B；主 session 每次准备收尾时，B 启动独立 supervisor session 检查是否真正完成。未完成时，由 B 将具体方向指令送回同一个主 session，继续执行；全部验收通过后结束监督。

这不是给现有独立 worker 增加一个可视化入口，而是改变新任务的执行归属和续跑入口。必须保持用户对主 session 的控制，避免重复续跑、旧判断覆盖新指令、用户暂停后被自动唤醒，以及模型声称完成但验收未通过。

## Solution

新任务默认采用主 session 监督模式。主 session A 始终承担 worker 职责；B 是独立运行的确定性控制进程；每次需要审核时新建的 supervisor session C 沿用现有 judge 职责，只读判断证据并提出方向。

采用同步 `Stop` hook 作为首版唯一续跑入口。这里的结束是“当前一轮准备停止”，不是关闭整个 session。主 session 准备停止时，hook 携带可验证的 session 与回合标识联系 B，等待 B 完成判断，再通过宿主支持的 hook 返回值决定是否继续。B 不在另一个 app-server 中恢复或执行主 session。

完整流程：

1. 用户在 A 中调用技能，保存目标、逐项验收、真实授权及可选限制，绑定 A 的真实身份，启动 B。
2. A 在原上下文中执行任务。仅当绑定任务处于活动状态时，相关 hook 才参与监督。
3. A 准备停止，`Stop` hook 将本次停止尝试及可追查证据提交给 B。
4. B 保存判断快照，启动独立只读 C，要求其核对全部验收项，并在卡点存在时调查已授权的替代路线及其他可推进事项。
5. C 返回严格校验的 `CONTINUE`、`DONE` 或 `WAIT_EXTERNAL`。
6. `CONTINUE`：B 通过仍有效的 hook 请求返回具体方向；宿主在 A 中继续工作。必须确认实际继续执行，不能把写入 hook 返回值当成已经开工。
7. `DONE`：B 完成固定独立验收及受保护验收文件检查，持久化完成状态并解除该任务的活动绑定，允许 A 停止。
8. `WAIT_EXTERNAL`：仅在必要外部条件有证据、替代路线与其他可执行工作均已检查后进入等待，说明缺失条件与恢复方法，停止自动催促。

本 SPEC 是单个完整功能规格。后续实现 tickets 由 `/to-tickets` 拆分；本次不另建总 SPEC 或子 SPEC。

## User Stories

1. 作为任务负责人，我希望调用技能的主 session 就是 worker，以便所有实际工作都发生在我正在查看的聊天中。
2. 作为任务负责人，我希望调用后自动启动独立 B，以便不需要手工运行另一套控制命令。
3. 作为任务负责人，我希望 B 绑定明确的主 session 身份，以便不会监督最近打开的无关聊天。
4. 作为任务负责人，我希望原上下文、模型、工具与权限继续由 Desktop 管理，以便启用监督不改变正常工作方式。
5. 作为任务负责人，我希望阶段性交卷触发独立检查，以便只完成一部分工作不会结束全部任务。
6. 作为任务负责人，我希望连续多次提前收尾仍会得到处理，以便监督不只催促一次。
7. 作为任务负责人，我希望每次判断使用独立只读 supervisor session，以便判断者不能修改项目来制造成功。
8. 作为任务负责人，我希望 supervisor 读取完整目标、授权及逐项验收，以便长聊天不会让目标缩小。
9. 作为任务负责人，我希望判断引用真实工具结果、产物和验收证据，以便不能只凭 worker 的最后一句话结束任务。
10. 作为任务负责人，我希望未完成时收到具体下一步，以便续跑能够产生可验证进展。
11. 作为任务负责人，我希望卡点出现时检查其他可行路线，以便不会反复执行已证明失败的方法。
12. 作为任务负责人，我希望个别事项受阻时先推进其他已授权工作，以便局部依赖不会冻结整个目标。
13. 作为任务负责人，我希望只有全部验收通过才记录 DONE，以便“看起来完成”不能代替交付。
14. 作为任务负责人，我希望固定独立验收失败时将真实失败交回 A，以便继续修复。
15. 作为任务负责人，我希望验收文件被修改时拒绝完成，以便不能通过削弱验收获得成功。
16. 作为任务负责人，我希望外部等待包含已尝试路线、为何没有其他工作及恢复条件，以便知道需要补充什么。
17. 作为任务负责人，我希望人工停止优先于 B 的指令，以便随时可靠叫停。
18. 作为任务负责人，我希望暂停后迟到的判断与验收无效，以便后台进程不会擅自重新唤醒主 session。
19. 作为任务负责人，我希望新的人类输入使旧判断失效，以便旧方向不会插入我刚调整的工作。
20. 作为任务负责人，我希望明确恢复后继续同一个主 session，以便保持上下文与成果。
21. 作为任务负责人，我希望重复事件不会产生重复判断或重复执行，以便回调重试不会重复修改项目。
22. 作为任务负责人，我希望同一主 session 最多有一个活动 B，以便不存在两个自动续跑入口。
23. 作为任务负责人，我希望 supervisor 不会被自己的结束 hook 再次监督，以便不存在递归调用。
24. 作为任务负责人，我希望 B 出错、hook 超时或进程退出时保留明确检查点，以便不会把故障误报为完成。
25. 作为任务负责人，我希望查询同时显示任务状态、B 是否存活与主 session 是否实际推进，以便进程存在不能冒充执行中。
26. 作为任务负责人，我希望查看最后一次判断、具体方向及等待原因，以便能理解监督为何采取当前动作。
27. 作为任务负责人，我希望未启用监督的聊天照常结束，以便插件不会影响其他 session。
28. 作为任务负责人，我希望默认没有任意总回合或总时长上限，以便任务不会因隐藏预算停止。
29. 作为任务负责人，我希望主动设置的限制跨恢复保留，以便监督遵守我的明确约束。
30. 作为任务负责人，我希望已存在的独立 worker 任务按原模式管理，以便升级不会静默迁移正在运行的工作。
31. 作为任务负责人，我希望安装后的插件在实际 Windows Desktop 上得到完整验收，以便模拟协议通过不被当成产品已经可用。
32. 作为任务负责人，我希望不兼容版本和未生效 hook 被明确报告，以便技能不会悄悄改回隐藏的独立 worker。

## Implementation Decisions

### 1. 执行归属与既有设计的变更

- 新调用 `needs-forever:supervise` 启动任务时，默认绑定调用它的主 session，主 session 就是 worker。任务控制方式与 `live` / `simulated` 证据分类分别记录，不能复用一个 mode 字段混淆两种含义。
- B 负责调度、事件关联、进程控制、判断和验收门禁；C 负责只读推理与方向建议；只有 A 执行用户项目任务。C 在产品语义上叫 supervisor，在现有内核语义上仍是 judge。
- B 不启动第二个 worker，不在自己的 app-server 中对 A 发起 `thread/resume` 或执行回合，不改用最近 session，不将 C 当作 A 的 subagent。
- 这项决定替代 #19 与 #32 对新任务“独立 app-server 创建独立 worker、不接管当前 Desktop”的产品边界。历史 SPEC、tickets 和验收记录保留；实现时同步更新现行入口说明和架构说明，不能继续把两种默认设计并列。
- 既有任务保留原控制方式、worker 身份和检查点语义；本 SPEC 不自动迁移或打断正在运行的独立 worker。对无显式模式的旧检查点须能识别为旧模式，不能猜成当前主 session。

### 2. 原会话身份、启动与兼容性

- 主 session 身份必须来自宿主可信上下文或结构化 hook 元数据，并与工作区和任务合同交叉核对。不能从标题、最近聊天、自然语言猜测或可任意伪造的命令行声明直接建立绑定。
- 若技能调用时无法取得可信身份，允许由同一宿主的首次结构化事件完成有凭据关联的绑定；绑定完成前不得报告已进入监督，也不得把待绑定状态冒充正常 ACTIVE。
- 启动前验证实际 Desktop 版本、hook 能力与信任状态、Node.js、判断器可用性及必要的本地通信。CLI 版本不能代替 Desktop 版本；安装成功、hook 配置存在或 B 启动成功都不证明 hook 已生效。
- 插件包含所需 hook 与运行包，安装副本能够独立运行。遵守宿主的 hook 信任流程；若需要用户审阅或重载，明确说明步骤和待验证状态，不能绕过信任或误报启用成功。
- 能力不足时返回明确的不兼容或待配置原因，保留可恢复信息；不能静默降级为独立 worker、自动升级 Desktop 或修改全局安全配置。
- B 以隐藏窗口的独立 Node.js 进程运行，具备任务级和主 session 级唯一租约，使用可核验的控制句柄管理生命周期，不能按遗留 PID 结束无关进程。

### 3. Stop hook 是唯一续跑入口

- 使用同步 `Stop` hook 联系 B 并等待判断；B 的 CONTINUE 结果通过宿主规定的 `decision` / `reason` 返回，继续发生在 A。不将异步 hook 的输出当作能够唤醒空闲会话的机制。
- 首版不同时实现 `codex queue` 或第二个 app-server 对 A 的续跑入口，避免两套发送和恢复机制竞争。后续若要加入异步投递，另立明确设计和验收，不作为本 SPEC 的隐式 fallback。
- hook 仅对已绑定且活动的任务生效；DONE、WAIT_EXTERNAL、PAUSED、未绑定聊天和独立 C 均不产生自动续跑。
- 用户补充的 opt-in 边界：只有明确执行 start / resume（内部 prepare）入口并经原生凭据关联建立活动绑定后，才产生监督效果。普通聊天、查看/搜索/打印命令或示例、doctor / status 不写入监督状态，不启动 B/C，不返回 CONTINUE；命令文本出现路径或 start 单词不算调用。宿主仍可能分发全局 hook 并展示通用 hook 活动，插件不承诺宿主零脚本调用或零通用 UI。
- 宿主可能在同一 turn 内继续，也可能生成新的 turn，实施前按实际版本核实。确认标准是原 session 中确有与指令关联的后续模型或工具活动，不机械要求更换 turn ID，也不把 hook 返回成功等同于模型已继续。
- 每次 CONTINUE 返回前保存完整方向、判断来源、合同版本和 delivery ID；随后核对实际继续活动。无法确认时保留未知结果，不能盲目重复投递。
- hook 等待、C 执行和 B 内部调用都有明确超时与取消边界。hook 请求已失效、宿主退出或通信断开后，旧结果不能被发送到另一个请求或新一轮用户工作。

### 4. 事件去重、顺序与人类输入

- 绑定身份至少区分主 session、任务、合同版本与运行代次；每次真实停止尝试另有唯一事件身份。回调重传沿用该事件身份，新的停止尝试生成新身份。
- 不能仅按 session ID 和 turn ID 去重：同一 turn 经过 Stop 续跑后可能再次合法触发 Stop。必须区分重复投递与下一次真实停止尝试，不能因 `stop_hook_active` 或旧的 handled-turn 集合而只监督一次。
- B 处理开始前和持久完成后均去重；同一事件最多有一个有效判断和一个有效方向投递。乱序、外国 session、过期运行代次与旧合同结果均被拒绝并记录原因。
- 新的人类输入使正在进行的旧判断和待发送指令失效，B 等待主 session 后续真实 Stop。普通补充指令不擅自扩大目标或授权；需变更合同的内容由主 session 明确更新并增加版本。
- 用户 Interrupt 或明确 pause 先持久化 PAUSED，再取消等待与自有判断/验收调用。人工停止不能被理解为任务完成，也不能被当作可重试服务错误自动唤醒。
- 不修改人类已有输入，不假扮用户批准权限，不自动回答主 session 的审批请求；主 session 的工具和审批继续由 Desktop 管理。

### 5. 判断输入、可行路线与证据

- 复用现有任务合同、证据快照、判断 Schema、输出校验及 CONTINUE / DONE / WAIT_EXTERNAL 语义，避免为新入口另建平行判断内核。
- 每次判断创建新的 C，使用独立 app-server 的只读工作区、受限网络和已验证工具隔离；不继承主 session 的写权限。C 的结束不触发主 session 监督，判断结束后归档并保存 ID。
- 快照包含原始目标、逐项验收、真实授权、合同版本、停止原因、关联工作证据、最近方向、已尝试路线和重复失败信息。
- 证据优先来自受支持的结构化 hook / 协议事件、只读产物核对和固定独立验收。停止时只有最后一条 assistant 消息不够；本地 transcript 可辅助诊断，不能成为唯一状态、身份或恢复协议。
- supervisor 必须核对每项验收，说明已完成、未完成和缺证据项。截断、缺失和不确定性要显式记录；worker 自述不能单独支持 DONE 或 WAIT_EXTERNAL。
- CONTINUE 必须包含具体可执行步骤、对应目标及预期证据。某路线失败时给出有实质区别且在授权内的路线；若其他事项可推进，先推进这些事项。不能把空泛“继续努力”、重复查询状态或反复提出已确认问题当作指导。
- WAIT_EXTERNAL 必须说明必要缺失条件、已尝试路线、为何无其他可执行工作和恢复条件。判断或传输故障不能伪装成用户缺少授权。

### 6. 完成门禁与验收隔离

- DONE 仍需覆盖全部验收项。任务配置了固定独立验收时，由 B 在明确授权和已验证隔离内执行，并检查受保护验收材料在执行前后未被削弱。
- 从任务绑定时记录初始受保护基线，不依赖“尚无 worker ID”才能初始化的旧假设；恢复时只能复用原基线，不能用当前已变更文件覆盖它。
- 独立验收不能借用隐含全权限执行入口。验收失败、超时或保护文件变化时，将真实结果作为证据返回 A，继续修复，不记录 DONE。
- 独立验收期间若收到人类新输入、暂停、合同变更或工作区成果变化，先前成功结果失效；重新获取适用证据后才能完成。
- DONE 持久化后释放活动绑定、停止本任务自动续跑并保留摘要。重复 Stop、迟到 C 结果与重启查询都不能重开任务；新增工作使用新任务身份。

### 7. 故障、检查点与恢复

- 复用现有持久状态、事件日志、判断快照、退避和恢复框架。状态保留 ACTIVE / WAIT_EXTERNAL / PAUSED / DONE；phase 至少明确工作、判断、验收、恢复和空闲的语义，不将进程存活与任务状态混为一谈。
- checkpoint 另存主 session 身份、控制方式、宿主兼容性证据、B 控制句柄、绑定运行代次、当前 Stop 请求、C 身份、已处理事件、待返回指令及执行确认。
- 可恢复判断或通信错误在有效 hook 请求的剩余期限内退避重试，重复失败进入调查或改变恢复路线。默认不设置隐藏总回合、总时长或总重试次数。
- hook 超时或请求丢失时立即使对应可投递资格失效，保留 RECOVERING 与真实错误，禁止返回伪造 DONE，也禁止创建第二个主 session 执行者。若只能明确恢复才可重建有效接入，状态必须说明需要该操作，不能持续报告正在推进。
- B 崩溃、Desktop 退出、机器重启或用户暂停后，通过明确 resume 恢复绑定的同一主 session，核对宿主和事件历史后再推进；不追逐 latest，不以另一个 app-server 启动主 session，不盲目重发未知结果。
- 某个 C 超时或异常时只清理 B 自己拥有的判断进程；不得为了重置 C 杀死 Desktop 或 A。

### 8. 状态、可观察性与现有任务

- 保留 start / status / pause / resume 的可管理能力，并为新绑定模式提供明确输入。status 只读，不启动 C、不执行验收、不唤醒 A。
- 状态明确展示任务控制方式、主 session ID、合同版本、status、phase、B 是否存活、最近判断和方向、hook 接入是否有效、实际续跑是否已确认、等待或恢复原因。
- `B live=true` 只证明 B 控制通道可达。只有真实主 session 活动才能证明正在工作；模拟证据必须标注 simulated，ACTIVE 且 B 不存活时须提示明确恢复。
- 原聊天可见实际执行及续跑方向，并能获取最后监督结论与状态入口。日志保留事件、session / turn / Stop 事件 / delivery / snapshot / C 的关联，证据保存前脱敏。
- 多个主 session 可分别有独立绑定和 B，但本 SPEC 不建设跨任务调度；不同绑定间的事件、租约和暂停不互相影响。
- 现有独立 worker 的查询、暂停和恢复行为作为兼容性回归保留，不自动接管或迁移任何正在运行的实际任务。

## Testing Decisions

### 已确认的行为边界

沿用本聊天已确认的真实 Desktop 原会话闭环验收方向。最高测试边界是安装后的插件入口与结构化 hook → 独立 B 和真实或替换 C → Desktop 中同一个主 session 的后续实际执行、任务产物和持久状态。对外检查暂停、续跑和验收结果，不断言私有函数调用顺序或内部进程拆分。

现有 Node.js 进程级插件集成测试、协议替换进程、真实 judge 边界、固定独立验收、暂停和恢复场景均可复用。新增 hook 宿主适配属于这一行为边界的外部依赖替身，不为内部模块增加专用测试接口。仅替换宿主或模型的用例标记 simulated，不能当作 live Desktop 证据。

### 验收场景

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| T01 | 从已安装插件在真实 A 中调用技能 | B 自动启动并绑定实际 A；没有创建第二个 worker；记录 Desktop 与 CLI 各自实际版本和 hook 生效证据 |
| T02 | A 完成三阶段中的第一阶段就准备停止 | C 检查后返回 CONTINUE，方向在 A 可见；同一个 A 实际完成下一步，不把 hook 输出当作执行确认 |
| T03 | A 连续两次提前收尾 | 两次均独立判断并继续；覆盖同一 turn 多次 Stop 的宿主行为或以明确标注的模拟场景补足；真实 Stop 不被错误去重 |
| T04 | 第一条路线确定失败，另一路线可行 | C 给出不同路线并由 A 实施；单项外部依赖不阻止其他已授权工作 |
| T05 | worker 自称全部完成或 blocked，证据不支持 | 拒绝 DONE / WAIT_EXTERNAL，继续补证据或推进工作 |
| T06 | C 返回 DONE，但固定独立验收失败或验收材料被改动 | B 拒绝完成；真实失败和保护检查交回 A；修复后才能再次验收 |
| T07 | 全部要求完成且独立验收通过 | 持久化 DONE，主 session 正常结束；绑定解除，重复事件不产生后续工作 |
| T08 | 用户在工作、判断或验收期间停止 / pause | PAUSED 先落盘；迟到成功和 CONTINUE 均不能唤醒 A；只有明确 resume 才可继续 |
| T09 | C 判断期间用户在 A 发送新指令 | 旧判断和待投递方向失效；A 处理新输入，后续以新的有效停止尝试重新判断 |
| T10 | 同一 Stop 重传、多个请求并发、旧合同或其他 session 事件到达 | 不重复判断或投递；其他 session 不受影响；同任务和同主 session 第二个 B 被拒绝 |
| T11 | C 本身结束或无关聊天正常结束 | 不发生递归监督，无关 session 无指令注入 |
| T12 | C 超时、输出无效或可恢复通信错误 | 原始错误可追查；有效 hook 期限内恢复；不推导 DONE，不因任意重试次数变成完成 |
| T13 | hook 超时、B 在返回前后崩溃、执行确认丢失 | 请求和投递结果按实际证据标记；旧结果不可投递；明确恢复不重复已执行步骤，不启动第二个 A |
| T14 | 必需外部条件确实只能由用户提供，且其他工作已尽 | WAIT_EXTERNAL 具备完整证据和恢复条件，只通知必要变化，不自动空转 |
| T15 | Desktop 关闭后重开、B 退出后明确恢复 | 在同一 A 身份下恢复；原合同、产物和基线保留；不在其他 app-server 中冒充原 Desktop 执行 |
| T16 | Desktop 不支持所需 hook、hook 未信任或身份无法核实 | 清楚报告不兼容或待配置，不误报已监督，不静默创建独立 worker，不绕过信任 |
| T17 | 只查询状态、达到用户显式限制、默认无限制 | status 不产生模型调用；显式限制持久暂停并跨恢复保留；未配置限制时不存在隐藏阈值 |
| T18 | 安装副本位于中文或含空格目录，插件更新后运行 | 不依赖开发仓库；参数不经不安全的 shell 拼接；hook、控制程序和内核包版本一致且可发现 |
| T19 | 旧独立 worker 检查点继续 status / pause / resume | 保持原模式和原 worker，不被迁移；其既有去重、隔离、验收和恢复回归通过 |
| T20 | 判断或验收期间主 session 工具、审批和用户配置被检查 | A 原有模型、工具、权限与审批流程保持由 Desktop 管理；C 只读隔离独立成立 |
