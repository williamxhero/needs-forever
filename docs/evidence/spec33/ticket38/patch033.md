# 0.3.3 Windows hook shell correction

The original Desktop acceptance chat remained `PENDING_NATIVE_HOOK`, with no main-session binding or controller B, after the user trusted 0.3.2 and restarted Desktop. This patch has not been installed globally or exercised in that chat. None of the local results below establish native Desktop acceptance.

The installed Windows commands used `%PLUGIN_ROOT%`. Official Codex `rust-v0.159.0` commit `687a119f0fcaace47e1f1abcc77cec6c813fd6da` discovers plugin hooks with two separate mechanisms: it replaces `${PLUGIN_ROOT}` in configured commands, and injects `PLUGIN_ROOT` into the command environment (`hooks/src/engine/discovery.rs`, plugin source environment and configured command construction). `hooks/src/engine/command_runner.rs` combines this source environment with the host environment. The actual user shell is PowerShell, which does not expand cmd's `%PLUGIN_ROOT%` syntax.

The fixed public boundary test reads the shipped hook definitions, performs the host placeholder replacement, supplies the host's `PLUGIN_ROOT` environment variable, and runs the configured commands through real PowerShell (`pwsh.exe`) and cmd. The copied package and working directory include Chinese characters and spaces. All six handlers receive ordinary uninvoked lifecycle events; the required result is exit 0, exactly `{}`, no stderr, and no workspace state files.

`windows-shell-red.txt` records the test before the fix: all six PowerShell commands fail with `MODULE_NOT_FOUND`; all six cmd commands pass. The fix changes only the six `commandWindows` values to the same `${PLUGIN_ROOT}/scripts/lifecycle.mjs` template already used by `command`. No shell detection, runtime behavior, trust handling or provenance handling changes.

`windows-shell-green.txt` records all twelve uninvoked event/shell cases passing and two positive simulated pre-tool → control preparation → post-tool flows binding the original fixture session and launching B. Those positive flows remain `mode=simulated`, `host.source=simulated`, `hook_effective=false`; they never drive the real acceptance chat. The affected installed main-session, supervision, controller, lifecycle and plugin suites are recorded in `windows-shell-regression.txt`.

The initial exploratory records `windows-shell-no-env-artificial-red.txt` and `windows-shell-no-env-artificial-green.txt` deliberately removed `PLUGIN_ROOT` from the child environment. That differs from the native host. Their cmd failures are artificial and must not be cited as native cmd failures; the final regression and red/green records use the correct host environment.

0.3.3 updates root/package-lock/plugin manifest versions and the README candidate version. `patch033-package.json` records archive parity and all 28 packaged file hashes against 0.3.2. The only packaged byte changes are the two plugin version metadata files and `hooks/hooks.json`; all runtime, scripts, skill instructions and marketplace bytes remain identical to 0.3.2. Historical 0.3.0–0.3.2 archives and receipts remain intact. Installing this candidate will change the six hook definitions and requires the host's actual trust review before native execution.
